# План исполнения: настоящий бесплатный прототип

Утверждённый ближайший результат: владелец проходит весь сценарий **локально либо на бесплатном закрытом стенде**, получает настоящий AI-текст в DOCX, видит сохранение/прогресс/библиотеку и проверяет оплату/рефералку в sandbox. Реальные деньги не обязательны и по умолчанию выключены. Продажи, касса, боевой сервер и production-правовые процедуры — следующий допуск, а не причина задерживать личный обезличенный тест.

Сначала запускается backend-агент, после его передачи — frontend-агент. Новые агенты сейчас автоматически не запускаются. [Backend prompt](prompts/backend-agent.md), [Frontend prompt](prompts/frontend-agent.md).

## Правила статусов

- ⬜ TODO — не начато.
- 🟡 IN_PROGRESS — ведётся работа.
- ✅ DONE — выполнены критерии, записаны проверки и доказательства.
- ⛔ BLOCKED — конкретно отсутствующий ключ/доступ/другая зависимость; указать, что требуется. Остальное продолжать.
- ⏭️ DEFERRED_PRODUCTION — только production-часть, исключённая из текущего личного теста. Это не DONE.

В каждом `Tasks/mvp/MVP-*.md` есть отдельный журнал исполнения. Агент обновляет свои строки, чекбоксы, результат/проверки/блокеры **в самом файле**, затем индекс Tasks. В совместном задании backend не отмечает работу frontend как готовую. Старое поле «Статус: TODO» заменить при изменении общего состояния. DONE всего файла только при полной его исходной приёмке; для прототипа достаточно явно завершённой части, production может остаться отложенной.

## Backend: последовательность

| Фаза | Задания | Результат |
|---|---|---|
| B1. Основа | MVP-01, локальная часть MVP-07 | Миграции, БД, вход/сессии, постоянные данные, короткий runbook запуска; закрыты исходные P0 |
| B2. Реальная генерация | MVP-02, MVP-03, локальный MVP-00 | Настоящий LLM, план/утверждение, worker/checkpoints, DOCX, реальный progress, библиотека API |
| B3. Покупка/бонусы | Sandbox MVP-04, backend MVP-09 | ЮKassa test checkout/webhook/refund, бонусный журнал и пять qualifying first purchases |
| B4. Передача | Backend часть MVP-08, MVP-00 | API contract, smoke runner/fixtures, примеры payload, local launch и отчёт; free deploy при доступности и необходимости |

Проверять каждую фазу, исправлять выявленное, писать короткий отчёт и продолжать следующую без запроса подтверждения на каждую фазу. При отсутствии LLM ключа/ЮKassa test credentials спросить один раз безопасный способ настройки и продолжать независимый код/тесты. Реальные external вызовы после появления ключа обязательны для соответствующей приёмки; unit mocks нужны для ошибок, но не заменяют доказательство живой генерации/checkout.

К концу B4 создать:

- `docs/backend/API-CONTRACT.md` + актуальную OpenAPI schema либо воспроизводимую команду её выгрузки: auth/CSRF, catalog/quote, plan/draft, order cash|bonus, job/progress, library/download, referral/reward/refund и коды ошибок.
- `docs/backend/LOCAL-RUNBOOK.md`: точные команды, env names без значений, test accounts/письма, start/stop/status/reset только test data, recovery, где DOCX и backup, режим оплаты.
- `docs/backend/BACKEND-HANDOFF.md`: выполнено/не выполнено, команды и результаты, оставшиеся frontend задачи/ограничения, URL/порты, порядок получения тестового заказа. Не включать пароли/ключи и приватные данные.

Не создавать пустую «идеальную» схему API отдельно от работающего сервера: контракт описывает фактические проверенные endpoints. Для тестового тарифа допустимо выбрать **300 ₽ / 300 кредитов**, `P=300`, reward=60; обозначить как sandbox настройку, не как утверждённую цену продаж.

## Frontend: последовательность после backend

| Фаза | Задания | Результат |
|---|---|---|
| F1. Вход/план | MVP-05 | Действующий Studio подключён к API, форма переживает вход, настоящий план/редактирование, checkout |
| F2. Полный сценарий | MVP-06 | Sandbox payment → настоящий job → честный progress → реальный DOCX/библиотека → reload/relogin |
| F3. Рефералка | Frontend MVP-09 | Ссылка, pending/available/history, выбор cash|bonus, пять покупателей → оплата бонусами |
| F4. Итог | Совместные MVP-00/MVP-08 | Browser E2E, понятный runbook для владельца; личный прототип готов или перечислены точные блокеры |

Backend defects, мешающие интеграции, можно исправить минимально и с проверками, обновив контракт/журнал; не требовать от пользователя передавать туда-сюда каждую опечатку. Изменение бизнес-правил не делать молча. Не ломать имеющийся дизайн и не переезжать на другой framework.

## Критерии готового личного прототипа

- [ ] Собственные обезличенные данные, закрытый доступ, тестовые почта/аккаунты; ключи только на backend.
- [ ] Регистрация/вход → форма → реальный LLM-план → утверждение → ЮKassa **test** checkout.
- [ ] Подтверждение оплаты проверено сервером; job единственный при повторном webhook/клике.
- [ ] Настоящий LLM-текст по утверждённому плану; DOCX открывается и содержит этот текст, не пример с заменённым заголовком.
- [ ] Прогресс соответствует сохранённым этапам, при задержке AI не двигается по таймеру; 100% только после файла.
- [ ] Файл/работа доступны после reload, relogin и restart сервера в пределах выбранного хранения; тест другого владельца отклонён.
- [ ] Негативный сценарий terminal failure → настоящий sandbox refund либо возврат бонусного резерва.
- [ ] Пять разных тестовых первых покупок → pending → available → бонусная оплата без настоящих денег.
- [ ] Mature pending ускорен только dev clock/test fixture, не сокращением production 14 дней; dev fixtures недоступны в production.
- [x] Есть отчёт проверок, реальные ограничения, точные команды запуска и шаги для владельца.

Если провайдер/ключ недоступен, можно передать подготовленный код, но нельзя ставить ✅ на живой сценарий. Бесплатное облако необязательно: успешного полного локального прохождения достаточно. Для Render отдельно проверить sleep/ephemeral storage/DB expiry; не обещать сохранность, которой тариф не даёт.
