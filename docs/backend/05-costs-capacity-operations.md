## Проверенные ориентиры

На дату 01.11.2026 [Timeweb Cloud](https://timeweb.cloud/services/cloud-servers) показывает 2 vCPU/4 ГБ/50 ГБ за 1080 ₽/месяц и 4 vCPU/8 ГБ/80 ГБ за 1800 ₽/месяц в выбранной на странице конфигурации. Регион, IPv4, резервное копирование и окончательную сумму подтвердить в заказе. Это ориентир доступного платного старта, а не доказанный самый дешёвый тариф всего рынка.

У [Cloud.ru free tier ВМ](https://cloud.ru/docs/virtual-machines/ug/topics/overview__free-tier) есть важное ограничение: новые бесплатные машины недоступны аккаунтам, зарегистрированным после 30.06.2026. У подходящего старого аккаунта — 2 vCPU/4 ГБ/30 ГБ, гарантированная доля CPU до 10%, IP/SNAT оплачиваются отдельно. Поэтому **не закладывать бесплатный VPS в базовый бюджет нового проекта**, даже если рекламная страница выглядит привлекательнее.

[Cloud.ru Object Storage](https://cloud.ru/docs/s3e/ug/topics/overview__free-tier): в standard классе 15 ГБ, 100 тыс. LIST/POST/PUT, 1 млн GET/HEAD ежемесячно без тарификации; первые 10 ТБ исходящего трафика также без тарификации в рамках условий. Лимит общий для организации, не на каждый bucket. Условия доступности storage подтвердить отдельно от ограничений ВМ; backups/версии тоже занимают объём.

Не выбирать иностранный бесплатный BaaS как основной auth/DB только из-за нулевой цены: наш целевой рынок и состав ПД требуют отдельной оценки локализации. Cloudflare/Vercel/Supabase не являются обязательными компонентами проекта.

## Расчётная модель

Число пользователей ниже — зарегистрированные; оно не равно DAU и параллельным генерациям. Все объёмы — сценарии, их нужно заменить измерениями.

```text
LLM/job = input_tokens/1000 * input_price
        + output_tokens/1000 * output_price
        + repair/retry/fallback + дополнительные сервисы
Месяц = VPS + IP + domain/12 + email + storage + backup + monitoring
      + jobs * LLM/job + acquiring + fiscalization + taxes + refunds/support
```

Пример **собственного расчёта**, не обещание провайдера: 20 тыс. входных + 30 тыс. выходных токенов при 0,20 ₽/1000 стоят 10 ₽. Резерв 30% на repair/retry → **13 ₽ за работу**. Число токенов включает весь pipeline; фактическая длинная работа может быть гораздо дороже.

| Сценарий | Допущение генераций | Расчёт LLM по 13 ₽ | Фиксированная инфраструктура: бюджет, не оферта | Итого до налогов/эквайринга/труда |
|---|---:|---:|---:|---:|
| Первая неделя, 50 приглашённых | По 1 ограниченной работе = 50 | 650 ₽ | 350–1000 ₽ при почасовой оплате; возможен депозит за месяц | 1000–1650 ₽ + домен/депозит |
| 100 зарегистрированных, месяц | 30 активных × 2 = 60 | 780 ₽ | 1300–2500 ₽ | 2080–3280 ₽ |
| 1000 зарегистрированных, спокойный месяц | 300 активных × 2 = 600 | 7800 ₽ | 2500–5000 ₽ при необходимости 8 ГБ | 10 300–12 800 ₽ |
| 1000 активно генерируют | 1000 × 2 = 2000 | 26 000 ₽ | 4000–10 000 ₽, зависит от пиков | 30 000–36 000 ₽ |

В фиксированные диапазоны заложен резерв на IP/почту/backup/storage/простой мониторинг; это плановые суммы, не проверенные отдельные тарифы. Домен и настройка кассы могут создать разовый платёж; стоимость труда и юридического сопровождения отдельно. Нельзя объявлять запуск «за 0 ₽», опираясь на промокод с ограниченным сроком.

Сервис может быть бесплатным клиенту первую неделю, если владелец ограничит число и объём работ. Для 50 работ при лимите 50 ₽/job верхняя LLM-экспозиция 2500 ₽; недельный stop-loss 1500 ₽ из раздела LLM остановит новые задачи раньше при дорогих результатах. Квоты согласовать так, чтобы не обещать всем работу, которую бюджет не позволяет выполнить.

## Экономика одной покупки

Пример, **не рекомендация цены**: продажа за 299 ₽, LLM 13 ₽, распределённая инфраструктура 10 ₽, условный полный processing fee 3,5% = 10,47 ₽, НПД при B2C 4% от выручки = 11,96 ₽, резерв возвратов 5% = 14,95 ₽. Остаток 238,62 ₽ до поддержки, маркетинга, разработки и иных расходов. Налог считать с применимой выручки, не автоматически с выплаты эквайера после комиссии.

Комиссии/кассу заменить цифрами договора; НПД применим только при праве на режим. Если LLM/job вырос до 100 ₽, остаток снизится до 151,62 ₽. Поэтому важнее stop-loss и успешность pipeline, чем экономия 100 ₽ на VPS. Без фактических данных не утверждать окупаемость или себестоимость ВКР.

## Нагрузка

Бета: API 1–2 процесса по замеру RAM, один LLM execution slot, один render slot; лимит активного job/user=1. Сумма memory limits должна оставлять ОС и PostgreSQL запас. Если 4 ГБ не хватает, дешевле перейти на 8 ГБ, чем ловить OOM. Swap — аварийная страховка, не плановая память конвертера.

Планировочные допущения для проверки: 5 минут генерации/job, 20 секунд render. Один LLM slot теоретически ≈12 jobs/час, один render slot ≈180/час, без запаса и сбоев. При загрузке 70% — около 8,4 LLM jobs/час. Эти числа не измерены на проекте. При 600 jobs/месяц средняя нагрузка мала, но 50 запусков перед дедлайном дают длинную очередь. Показывать позицию/ожидание и ограничивать новые старты.

Polling: 100 одновременно открытых jobs / 5 секунд = 20 запросов/сек; 1000 = 200/сек. Не опрашивать все готовые работы. Ответ прогресса маленький, без AST; индексированный запрос/короткий cache. На 1000 **одновременных** генераций текущий односерверный план не рассчитан.

Целевые пороги для первого load-test: CRUD p95 <500 мс при 20 RPS без внешнего LLM; error rate <1%; память <80%, диск <70%, очередь в обычное время <5 минут. End-to-end p95 и сроки генерации установить после benchmark, отдельно учитывать время в очереди. Старое обещание PRD «полная работа за 120–180 секунд» пока не подтверждено.

## Как масштабировать

1. Сначала измерить длительность каждого шага, tokens, memory peak и queue age.
2. Поднять VPS до 8 ГБ и ограниченно увеличить LLM concurrency, если хватает RPM/TPM провайдера и бюджета.
3. При OOM/CPU конвертации вынести render worker на второй российский VPS; S3 уже позволяет общие файлы без shared filesystem.
4. Вынести PostgreSQL в managed/отдельный сервер при критичности восстановления, I/O bottleneck или недостаточном RPO, а не по числу регистраций.
5. Добавлять API replicas и балансировщик только при реальной нагрузке; сессии и jobs уже в общей БД. Не держать state в процессе API.

## Обязательная эксплуатация

- Ubuntu LTS/Debian с обновлениями, pinned container versions/digests, TLS с автообновлением, firewall. Наружу 443 и ограниченный SSH; порт 80 только redirect/ACME.
- Secrets вне репозитория и образа, разные test/prod учётки. Fail-fast при mock key/default password в production.
- Ежедневный зашифрованный `pg_dump` + файлы в отдельное хранилище/аккаунт в РФ. Поскольку billing критичен, делать дополнительные dumps/backup после значимых операций по возможности; перед платным запуском целевой RPO согласовать явно. Для RPO ≤15 минут добавить WAL archiving/PITR или managed backup, не выдавать ежедневный dump за такой RPO.
- Бета: проектный RPO ≤24 часа, RTO ≤4 часа после **учения восстановления**. Платный пилот: целевой RPO ≤15 минут для БД или формально принятый владельцем больший риск с процедурой reconciliation платежей. Внешний платёж сверяется с эквайером, он не восстанавливается из клиентского браузера.
- Restore в чистую машину/БД, проверка sample files/ledger, повторное применение deletion tombstones, сверка платежей и outbox. Backup без успешного восстановления не считается готовым.
- Метрики: latency/error rate, oldest queued job, stuck leases, LLM cost/day, reserve/actual divergence, payment pending age, receipt/refund failures, S3 errors, RAM/disk, last backup/restore.
- Alerts только с действием: job завис, бюджет 70/90/100%, backup просрочен, диск 80%, webhook/касса не проходят. Telegram/email админа без ПД пользователя и токенов.
- Deploy: миграции expand/contract, backup, smoke, rollback образа без разрушения схемы. Не запускать одновременно несколько неконтролируемых Alembic upgrades.
