# 06. Оплата, учёт и возвраты

> Актуальный MVP: [summary.md](summary.md), [рефералка/прогресс](10-referrals-and-progress.md), [зарубежные API/бесплатный тест](11-foreign-api-and-free-prototype.md) приоритетнее этого расширенного документа. Реферальный бонусный баланс обязателен; покупка кредитов/промокоды не нужны. Российские LLM исключены. Старые предложения по paid wallet, S3 работ, PDF и масштабированию отложены. Аудит безопасности и применимые юридические обязанности сохраняются.


## Выбор для MVP

Рекомендация: **ЮKassa, размещённая платёжная страница, СБП + карты**, одна интеграция. Предполагаемое «UCAS» трактуется как ЮKassa; если имелся в виду другой сервис, сравнить его до реализации. Данные карт в наше приложение не попадают. СБП оформлять как merchant payment с order ID, суммой и уведомлением, а не как перевод на личную карту.

| Вариант | Плюс | Ограничение/решение |
|---|---|---|
| ЮKassa | API, СБП/карты, hosted checkout, варианты чеков | Получить разрешение на категорию сервиса, тариф и схему для НПД/ИП |
| CloudPayments | Реальная альтернатива эквайринга и фискальных интеграций | Запросить договор, комиссии, условия для нашего статуса; не интегрировать два эквайера сразу |
| Прямой СБП банка | Может быть дешевле по комиссии | Отдельная merchant API, onboarding, refunds и чеки; сравнить полную стоимость |
| QR на личный счёт/статичная картинка | Просто показать | Нет надёжной автоматической привязки и подтверждения; не использовать как основной SaaS checkout |

[Банк России о СБП](https://cbr.ru/PSystem/sfp/) описывает систему платежей; конечная комиссия посредника, категория бизнеса, налоги на комиссию и фискализация зависят от договора. Нельзя обещать «0,4% для любых услуг» или отсутствие чеков из-за QR. На [странице тарифов ЮKassa](https://yookassa.ru/fees/) сверять полную стоимость, включая применимые налоги/дополнительные сервисы, и получать итоговое предложение в кабинете.

Для 50 пользователей экономически важнее отсутствие обязательного месячного платежа и ручной сверки, чем десятые доли процента. Рекуррентные платежи, сохранённые карты, подписки и автоматическое списание отложить.

## Что продаём

Платная единица — пакет услуг генерации/редактирования с ясными лимитами. В UI можно оставить кредиты, но в оферте объяснить содержание услуги, цену, порядок расхода, срок доступа и возврат остатка. Не называть кредиты денежным кошельком, не добавлять переводы другим пользователям.

Вариант ещё проще — заказ одной работы с включённым числом исправлений. Он уменьшает сложности предоплаты, кредитных остатков и возвратов, но потребует изменения текущего UI. В этом пакете выбран ledger кредитов для сохранения интерфейса; перед реализацией владелец утверждает вариант в BE-002.

## Надёжный процесс оплаты

1. Клиент передаёт `product_id`, не доверенную цену. Backend фиксирует snapshot тарифа, RUB в копейках, owner, offer_version, receipt customer email и local order ID.
2. В БД создаётся order/payment intent с уникальным idempotency key. Запрос провайдеру выполняется **после commit без удержания row lock**. При таймауте повторить с тем же ключом и сверить состояние, не создавать новую покупку вслепую.
3. Использовать официальный Python SDK или небольшой typed `httpx` adapter к документированной API. Синхронный SDK не блокирует async event loop: отдельный thread/worker. Выбор зафиксировать после проверки поддерживаемой версии. Secret только backend; return URL только из server-side allowlist.
4. В webhook разобрать provider-specific payload. Для ЮKassa не придумывать общий `X-Signature`: в [официальной инструкции](https://yookassa.ru/developers/using-api/webhooks) указаны проверки статуса объекта/IP. Основная наша проверка — authenticated GET платежа через серверную API, сверка payment ID, merchant/recipient, `status`, `paid`, amount, currency и связи с local order. IP-фильтр — дополнительная мера с корректным trusted proxy.
5. Событие помещается в durable inbox; только после надёжной записи ответить 200, обработку можно продолжить worker. При недоступной БД не подтверждать получение. Повторы — штатный случай; ключ дедупликации строится из стабильных полей провайдера, не из придуманного event UUID.
6. Успешный платёж одним commit меняет state и выдаёт credit lot + ledger grant. UNIQUE provider payment ID и operation ID запрещают повторное зачисление даже при конкуренции.
7. Redirect браузера не подтверждает оплату. UI опрашивает backend order status. Watchdog сверяет pending orders с провайдером при потерянном webhook.

Разделять `payment succeeded`, `credits issued`, `receipt succeeded`: это разные подтверждения. При сбое чека — очередь повторов, alert и работа по согласованной фискальной схеме; не игнорировать ошибку. Тестовая ЮKassa и mock billing обязаны быть запрещены в production.

## Резервирование генерации

`available → reserved → captured` при готовых обязательных файлах. При конечной технической ошибке — `released`. Денежная оплата за пакет уже прошла; release возвращает единицы услуги на доступный баланс, а не автоматически делает банковский refund. Пользователь всё равно может подать требование возврата денег.

Каждому reserve/capture/release соответствует уникальная операция и job. Конкурирующие старты используют транзакционные блокировки и CHECK неотрицательного остатка. Финансовый commit контролируется сервисом верхнего уровня; низкоуровневый `spend_credits` не делает самостоятельный commit между созданием job/outbox.

## Возвраты

Подробное правовое основание в [юридическом разделе](08-russian-legal-launch.md). Отказ «PDF скачан, поэтому возвратов никогда нет» не использовать.

| Ситуация | Продуктовая политика для пилота |
|---|---|
| Двойной платёж/сервис не запустился | Полный возврат соответствующей покупки |
| Job завершился технической ошибкой | Автоматический release; предложить повтор или денежный возврат по обращению |
| Неизрасходованный оплаченный пакет | Вернуть неиспользованную сумму с учётом законной квалификации и реально оказанной части |
| Частично использованный пакет | Прозрачная детализация по credit lots, не произвольный штраф |
| Некачественный результат | Зафиксировать недостаток, рассмотреть исправление/уменьшение цены/возврат по закону и оферте |
| Просто передумал после полностью оказанной надлежащей услуги | Индивидуальное рассмотрение и мотивированный ответ; возможность отказа зависит от договора и фактов |

Рабочая процедура: заявление → подтверждение владельца заказа → фиксация суммы/основания → остановка новых расходов спорного остатка → операторская проверка → refund intent с idempotency key → провайдер → подтверждение → бухгалтерский/НПД чек коррекции/возврата по применимой схеме → уведомление пользователя. Не считать HTTP 200 от create refund окончательным возвратом.

Обеспечить инварианты: суммарный confirmed+pending refund ≤ исходная оплата; одна кредитная единица не расходуется и не возвращается одновременно; частичный возврат не аннулирует весь чек автоматически. В ledger отдельные компенсирующие записи, исходную историю не переписывать. Деньги возвращать по исходному платежу через провайдера; не собирать номера карт в чатах.

На MVP решение принимает оператор с MFA и аудитом, API делает автоматическую безопасную проводку. Учёт причин/сроков и экспорт подтверждений обязателен; автоматический юридический отказ алгоритмом не нужен.

## Чеки

[ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/basics) различает компании/ИП и самозанятых: последним нужно регистрировать доход в «Мой налог» и передавать чек покупателю. Подтвердить, доступна ли автоматизация именно в выбранном подключении; уведомление об оплате не заменяет налоговый чек.

Для ИП/ООО определить 54-ФЗ, ККТ/сервис чеков, ОФД и ФН, применимые реквизиты и необходимость чеков предоплаты/зачёта/возврата. Покупка кредитов до генерации может быть авансом; нельзя считать один чек «полный расчёт» заведомо правильным для любого сценария. Схему согласовать с бухгалтером и эквайером до боевой оплаты.

## Уточнение MVP: реферальные бонусы

Кредиты теперь остаются только как реферальное вознаграждение, не покупной пакет. Checkout cash|bonus, без смешанной оплаты. При технической ошибке cash → полный provider refund, bonus → release исходного резерва. Completion/refund денежной первой покупки пересчитывает pending/available reward, не блокируя законные возвраты. Формулы, сроки, поздние отмены и debt — в [документе 10](10-referrals-and-progress.md), который приоритетен для реализации.
